## 1. What the build proves

Three things must work end-to-end on an Android device:

1. **MWA wallet connect** — rider taps Connect Wallet → MWA launches the
   installed wallet (Phantom/Solflare/Backpack or Seed Vault on Seeker)
   → rider approves → pubkey renders in Boulder Roller.
2. **Seed Vault detection** — on Seeker or on any Android with the Seed
   Vault Simulator APK, the Wallet screen surfaces "Seed Vault detected"
   above the Connect button.
3. **Sign demo memo** — rider taps Sign Demo Memo → wallet signs a
   devnet Memo Program tx → Boulder Roller shows the signature + a
   Solscan link that renders the tx on-chain.

If any of those three break, the grant video is in trouble. If all three
work, the narrative from the grant draft ("record a ride, detect the
climbs, sign the vault completions, earn rewards -- all from a single
device") has its foundation.

## 2. Prerequisites

### 2.1 Tools

- Node 20+ (match `mobile/package.json` `engines` if present)
- npm (Yarn is not used in this repo)
- Android SDK + platform tools (`adb`) — via Android Studio is easiest
- An Android device API 33+ or an emulator with Google Play
- One of:
  - **Seeker** (real hardware; Seed Vault is the native wallet)
  - **Phantom app** installed on Android (works on any Android; gets
    MWA authorize + sign via intent)
  - **Solflare app** on Android
  - **Seed Vault Simulator APK** (dev path for testing the Seed Vault
    UX without owning a Seeker — download from Solana Mobile docs)

### 2.2 Repo env

Boulder Roller mobile is an Expo bare workflow project. Key paths:

```
mobile/
  app.config.ts        # Expo config (ExpoConfig)
  app.json             # Legacy; app.config.ts wins
  eas.json             # Build profiles
  package.json         # Deps — don't edit without a reason
  ios/                 # Present; autogenerated by prebuild
  # android/ does not exist yet — prebuild generates it on first
  # Android build (see §4).
```

### 2.3 Secrets

The app reads env vars at build time via `app.config.ts`. For an
Android dev build you need:

| Var | Required? | Source |
|-----|-----------|--------|
| `API_URL` | Yes | Staging droplet IP or `https://api.boulderroller.org` |
| `PRIVY_APP_ID` | Yes (auth flow) | Privy dashboard (`cmjp145cl008xl70clr2ho821` is the dev default) |
| `PRIVY_CLIENT_ID` | Optional | Privy dashboard |
| `SENTRY_DSN` | Optional | Sentry project (blank = disable) |

Set them in an `.env` file in `mobile/` (gitignored) or inline when
running commands.

Expo Go cannot host these native modules. Every Android build below

## 4. Generate the Android native project

The repo ships `mobile/ios/` but not `mobile/android/`. First Android
build:

```bash
cd mobile
npx expo prebuild --platform android
```

This creates `mobile/android/` from `app.config.ts`. Commit it only if
the team decides to pin native files in git — current convention is to
regenerate per build. Rerun after any `app.config.ts` change.

### 4.1 Android permissions sanity-check

After prebuild, verify `android/app/src/main/AndroidManifest.xml`
contains the permissions declared in `app.config.ts`:

- `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`,
  `ACCESS_BACKGROUND_LOCATION`
- `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`
- `POST_NOTIFICATIONS`
- `BLUETOOTH`, `BLUETOOTH_CONNECT`, `BLUETOOTH_SCAN`

MWA itself does not need a permission — the wallet app owns the UI;
Boulder Roller just launches an intent.

## 5. Build — two paths

### 5.1 EAS Cloud build (recommended)

EAS is the supported path for signing / preview / production builds.

```bash
cd mobile
# One-time: link this checkout to your EAS project.
npx eas login
npx eas init     # if no EAS project yet

# Development build — dev client with Fast Refresh, internal distribution
API_URL=http://<staging-ip>:8080 PRIVY_APP_ID=<dev-app-id> \
  npx eas build --profile development --platform android

# Preview build — full APK, internal distribution, for Alexei's Seeker
API_URL=http://<staging-ip>:8080 PRIVY_APP_ID=<prod-app-id> \
  npx eas build --profile preview --platform android
```

EAS returns an APK download link on completion. `adb install <path>` it
to the device.

`eas.json` currently has `"REPLACE_WITH_EAS_PROJECT_ID"` as the project
id — first run of `eas init` replaces that. Commit the resulting
`app.config.ts` `extra.eas.projectId` so subsequent builds reuse the
same project.

### 5.2 Local build (no EAS, Android Studio path)

For dev iteration on localhost backend:

```bash
cd mobile
API_URL=http://localhost:8080 PRIVY_APP_ID=<dev-app-id> \
  npx expo run:android
```

This compiles the native project directly and installs to the connected
device / emulator via `adb`. Faster for tight dev loops; does not
produce a signed APK.

## 6. On-device test flow (5 minutes)

The flow that the grant video needs to prove:

1. Launch Boulder Roller on the device. Sign in (Privy social or
   wallet).
2. Go to **Profile → Wallet** (section at the bottom of Profile).
3. **Signed In As** row shows the rider's auth wallet (Privy embedded
   or SIWS-connected).
4. **Protocol Wallet (MWA)** section:
   - On Seeker with Seed Vault enabled: "Seed Vault detected..." banner
     appears.
   - Tap **Connect Wallet** → the OS picks a MWA-compatible wallet
     (Phantom on Pixel; Seed Vault on Seeker) → rider approves →
     pubkey renders.
   - If the connected pubkey matches the auth wallet, a green
     "Matches your sign-in wallet" note appears. If not, the app warns
     the rider that protocol outcomes accrue to whichever wallet
     signs.
5. Tap **Sign Demo Memo**:
   - Memo text is visible above the button: `Boulder Roller — MWA
     test signature`.
   - Wallet opens (Seed Vault double-tap or wallet-native confirm),
     rider approves.
   - Boulder Roller renders the signature prefix + a **View on Solscan**
     link and a **Copy** button. Tap Solscan → confirms the memo tx on
     devnet.

If all three work, you have a grant-video-ready device.

## 7. Known gotchas

### 7.1 Expo Go is not an option
`@solana-mobile/mobile-wallet-adapter-protocol` and `seed-vault-lib`
are native modules. They require a dev client or full APK — Expo Go
does not ship their binaries.

### 7.2 New Architecture is on
`app.config.ts` sets `newArchEnabled: true`. MWA + Seed Vault modules
currently support the new arch (verified on the current dep versions),
but if Android build fails with a Codegen or TurboModule error, the
workaround is to flip `newArchEnabled` to `false` temporarily and
rerun `expo prebuild`.

### 7.3 Connecting to localhost API from a device
Android devices cannot reach `localhost` — use the machine's LAN IP
(`API_URL=http://192.168.x.y:8080`) or port-forward `adb reverse
tcp:8080 tcp:8080`. Emulators can use `10.0.2.2` to reach the host.

### 7.4 MWA with no wallet installed
On a stock Android with no Phantom/Solflare/Backpack and no Seed
Vault, `connectWallet()` throws
`SolanaMobileWalletAdapterError.ERROR_WALLET_NOT_FOUND`. The
WalletScreen classifies this and shows: "No MWA-compatible wallet
found on this device. Install Phantom, Solflare, or Backpack — or use
a Seeker." Don't ship a device to a reviewer without a wallet app
pre-installed.

### 7.5 Seed Vault availability vs wallet connection
`isSeedVaultAvailable()` returns whether the device has the Seed Vault
system app or the Simulator APK. It doesn't tell you anything about
whether the rider has a seed loaded — that happens behind the MWA
authorize handshake. So the "Seed Vault detected" note means "your
signing path can route through Seed Vault", not "you are already
signed into Seed Vault".

### 7.6 iOS is intentionally disabled
`isMwaSupported()` returns `false` on iOS. The screen renders a clear
unsupported-platform note. iOS path (Phantom / Solflare deeplinks) is
tracked separately, not in this bead.

### 7.7 Memo Program tx is free but needs a recent blockhash
`signMemoTransaction` fetches a blockhash from
`https://api.devnet.solana.com`. If devnet is having a rough day, the
fetch may hang. If `Sign Demo Memo` seems stuck, check devnet status
at `status.solana.com` before debugging the app.

### 7.8 Signed-in wallet != MWA wallet is legal, not an error
Per MOBILE_TRUTHS §10, authentication identity and protocol identity
may coincide but do not have to. A rider who logs in with Google
(Privy embedded wallet) can MWA-connect a hardware wallet for signing.
The Wallet screen surfaces this as an amber note, not an error.

## 9. What still needs a real Seeker to verify

Dispatcher-flag items — the items below are believed correct from
code review but need hardware-level sign-off before the grant video is
recorded:

- Seed Vault native double-tap UX renders on the Seeker's lock-screen
  style prompt (not just an ordinary wallet modal).
- MWA authorize against Seed Vault on Seeker returns a pubkey whose
  private key never leaves the TEE.
- `isSeedVaultAvailable(true)` returns `true` on Seeker without the
  Simulator APK (should be baked into firmware).
- The memo tx actually lands on devnet from a Seeker (network layer,
  not wallet layer — might surface firewall / VPN behaviors unique to
  the device).
- Background GPS + foreground service notification appears as expected
  when a ride is recording alongside wallet interactions.

Alexei has a Seeker. Route items 1-4 to him for a quick pass. Item 5
is out of scope for this bead (ride recording is bead `5hdl.4` / other
M-beads).
